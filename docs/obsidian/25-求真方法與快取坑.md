# 求真方法論 + 可訂狀態不同步的快取坑（反思）

> 這篇是「修一個真 bug + 反省態度」的紀錄。**前面幾次把「真 bug」誤判成「使用者看錯場」，錯在方法與態度，而不只技術。**

---

## 一、態度與求真（給自己/後續 session 的鐵律）

### 大忌：拿 API 證據反駁使用者看到的畫面

- 使用者說「畫面顯示 19:30 綠」，我用 `curl` API（回 23:00,23:30 可訂）推斷「資料是對的」→ 反覆說「你看錯場」。
- **錯在哪**：使用者看到的螢幕就是真相。`curl` 是我的假設，螢幕是他的現實。**兩者不一致時，要懷疑「前端/中間層」，不是懷疑使用者眼睛。**

### 正確查 bug 順序

```
① 重現使用者看到的（用 pilot/瀏覽器開同一頁、同場地同日期）
② 若 API 對、畫面錯 → 查前端狀態管理 + 瀏覽器/中間層快取
③ 才回頭查 DB / server 邏輯（通常是無辜的）
④ 逐層往上挖，不要急著證明「使用者錯」
```

### 一句話

> **先信使用者，再懷疑系統；先重現畫面，再挖資料。** 不要用「我查到 X 正確」來否定「你看到 Y」。

---

## 二、真 bug：可訂狀態不同步（LINE LIFF 快取）

### 症狀

- 建立訂位頁「明明該時段已訂”，卻顯示可訂（綠 NT$400）。
- 例如 7號場 09/02，DB 只有 23:00,23:30 可訂，但手機畫面 19:30 起顯示全綠。

### 根因

`/api/bookings/available`（建立訂位）與 `/api/bookings/week`（查閱場地）原本回：

```
cache-control: public, max-age=0, must-revalidate
```

- `max-age=0` 只是「要 revalidate」，但 **LINE LIFF 內建瀏覽器 / 手機 Safari 仍可能緩存**。
- 切換場地、切換日期時，前端 `fetch` 到**被緩存的舊「可訂」狀態** → 顯示過時。

### 已修（2026-08-23）

兩支 API 都改：

```
cache-control: no-store, max-age=0
```

強制每次請求即時查 DB，不再緩存。已上線正式 dearfly.com.tw。

### 驗證

```bash
curl -D - -o /dev/null "https://dearfly.com.tw/api/bookings/available?courtId=seed-court-7&date=2026-09-02" | grep -i cache-control
# 應回 cache-control: no-store
curl -s "https://dearfly.com.tw/api/bookings/available?courtId=seed-court-7&date=2026-09-02"
# 7號場 09/02 應只列出 23:00,23:30 可訂
```

---

## 三、通用原則（防再踩）

- **凡「顯示與資料似乎不同步」→ 先懷疑前端/快取層，再查 DB。**
- **凡「訂位/庫存/餘額/可訂」這類對時效敏感的 API → 一律 `Cache-Control: no-store`**（LINE LIFF 對這類特別容易快取）。
- **查 UI 同步問題 → 用 pilot/瀏覽器真實重現使用者畫面**，別只 curl API。
