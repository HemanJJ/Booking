# 老闆習慣與協作規範（給未來 session 的 onboarding）

> 這篇不是技術文件，是「**怎麼跟這位老闆共事**」的手冊。新 session 接手前先看這篇，
> 就能少踩他踩過的坑、少教他一輪有的沒的。**目的：不用每次重新「教育」AI。**

---

## 〇、他是誰（30 秒理解）

- **老闆**，不是工程師。經營**羽球館**（迪飛太平，7 面場）+ **智慧拍櫃租借**（5 家分店）+
  **羽拍穿線服務** + **運動商城/進銷存**。
- 品牌原名 **DiFly**，已更名 **Dearfly**（網域 `dearfly.com.tw`、`shop.dearfly.com.tw`）。
  檔案/目錄仍常寫 `difly-*`、`booking`，**看到舊網址 `difly-booking.vercel.app` 要當成舊規格**。
- 靠 **vibe coding**（做中學 + AI 代寫）把一套能營業的系統養起來，所以他認得「需求、流程、結果」，
  **不認得**也**不需要**懂「實作細節、內部資料結構、確切函式名」。
- 關鍵帳號/真相來源：見 [[21-營運晴雨表]]「所有平台一張表」、[[17-災難復原]]、[[10-資安與金鑰]]。

## 一、他的做事習慣（長期不變的）

1. **文件化一切**：從對話紀錄結構化成知識庫，每篇有 frontmatter（`tags`/`created`）、
   `# 標題`、開頭 `> 引言`、編號章節（一、二、三）、表格、code block、結尾 `## 相關` wikilink。
   **新文件一律照這個格式寫。**
2. **把「地雷/坑」明寫出來**：他不追求每篇都美，追求「**下次別再犯**」。
   所以會有 [[19-UI踩坑紀錄]]、[[25-求真方法與快取坑]] 這種「踩坑+根因+修法」文。
   **新踩的坑 → 也寫一篇或加進現有篇，別只嘴上說。**
3. **靠自動化 + 一鍵工具補救健忘**：`🩺 一鍵健康檢查.command`、`💾 備份Neon資料庫.command`、
   `🚀 Dashboard.command`、launchd 每週自動。**能用「雙擊就能用」的實體工具解決的，就別叫他記。**
4. **對「萬一」極度焦慮**：生意/資料/金鑰全放雲端，Mac 只是工具；備份要做**三層**
   （GitHub 碼 + Neon PITR 資料 + 每週 pg_dump→iCloud），並留**紙本人工接單**當最後保險。
   **提方案時，永遠順帶給「出事時怎麼接手」的後路。**
5. **喜歡動詞式的具體指令 + emoji 標記**：文件裡 `📞 電話訂位`、`🔐 智慧拍櫃`、
   `🩺`、`💾`、`🚀`。跟他溝通就是用**一句話講清楚「要幹嘛、給誰看、什麼算完成」**。

## 二、怎麼對他說話（溝通風格）

- **一句話、結論先行**：先講結果，再講為什麼。他不想讀長推導。
- **說人話，不要術語**：說「資料庫」就好，別說「PostgreSQL driver adapter / Query Compiler」。
  真的要講技術，就**補一句人話解釋**。
- **用表格對比、用 code block 給可直接跑的指令**：他習慣看「舊 vs 新」「自動 vs 手動」「會用完 vs 免費」。
- **實體結果優先**：他能看到的是「畫面上出現了什麼、客人能訂位了嗎」。
  講話貼著**使用者會看到的東西**講，別講「我改了哪個 function」。

## 三、對 AI / session 的鐵律（反覆踩過的）

> 底線：**先信使用者，再懷疑系統；先重現畫面，再挖資料。**

1. **不要拿 API 證據反駁「使用者看到的畫面」**。
   他說「畫面顯示 19:30 綠」，就是 19:30 綠。你的 `curl` 只是假設，他的螢幕是真相。
   （教訓見 [[25-求真方法與快取坑]]）
2. **查 UI 不同步的順序**：① 用 pilot/瀏覽器重現他看到的同一頁同條件 →
   ② 查前端狀態管理 + 瀏覽器/中間層快取（LINE LIFF 特別愛緩存）→ ③ 最後才查 DB/server。
   **不要急著證明「他錯」。**（[[26-Dearfly前台與LIFF網址清理]] 我又犯了同一錯，已記取）
3. **訂位/庫存/餘額/可訂這類時效敏感 API → `Cache-Control: no-store`**。
   （[[25-求真方法與快取坑]] 根因）
4. **UI 開發硬規則**（[[19-UI踩坑紀錄]]「給新 session 的鐵律」）：
   - 功能必需樣式（定位/遮罩/置中/捲動/狀態色）→ **內聯 `style`**，別依賴 Tailwind class（v4 在部分瀏覽器整批失效）。
   - modal **一定要能捲**，任何視窗高度底部按鈕都要看得到。
   - 互動用 **Mouse Events + onClick**，別只用 PointerEvent（舊瀏覽器不支援）。
   - **通知要克制**：cron 自動化不逐筆發 LINE，只寫 log；只有人工動作/重大事件才發。
   - 改完 UI **用縮小視窗（約 700×500）自測**，別只在開發機大螢幕看。
5. **商/務話別亂改**：他重視「使用者看到的」；不是他要求的，別擅自「改良」設計。
6. **改任何東西 → 走完 git 4 步**（`add→commit→push→deploy`）才算完。
   **commit+push=備份 程式；deploy=讓客人看到新版。兩件事！**（[[22-維護心法]]）

## 四、反模式（千萬不要）

- ❌ 拿 `curl` / 資料庫結果說「你看錯場／資料是對的」。
- ❌ 改完 UI 只在大螢幕看，沒縮小視窗、沒測非 Chrome 瀏覽器。
- ❌ 自動化動作逐筆發 LINE、一次發一堆通知（曾把 LINE 每月 200 則額度一次用完）。
- ❌ 用 `prisma db push` 改線上 Neon schema（要手動 `ALTER TABLE ADD COLUMN`）。
- ❌ 用 `Path.exists()` 判斷 `~/Desktop`、`~/Documents` 的路徑（macOS TCC 會誤判為 True）。
- ❌ 把金鑰/`.env`/token 貼進 GitHub 或檔案公開（金鑰只在雲端後台 + 急救包）。
- ❌ 用 `difly-booking.vercel.app` 當「正式網址」——正式是 `dearfly.com.tw`。
